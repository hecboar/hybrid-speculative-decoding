## B1 — [RESOLVED 2026-07-07] GPU CUDA stack cannot run: torch has no sm_120 kernels

**RESOLUTION (2026-07-07):** Upgraded to **torch 2.11.0+cu128** (plus
transformers 5.13.0, datasets 5.0.0, accelerate 1.14.0, scipy 1.17.1). A
1024×1024 bf16 matmul and real model forwards now execute on the RTX PRO 4500
Blackwell (sm_120) without the "no kernel image" error. Verified by loading and
generating with **Falcon-H1-0.5B** (36 layers, 521M params, 1.04 GB VRAM) and
**Qwen3.5-0.8B** (24 layers = 18 linear + 6 attention, 752M params, 1.50 GB
VRAM) — both patchable by the DraftModeController. GPU work (E0.1/E0.3/E0.5 and
Phases 1–5) is UNBLOCKED.

**Standing caveat (PLAN constraint 2):** this GPU is **NOT an L4**. Every
*latency / wall-clock* number produced on this pod is non-canonical and must be
labelled "measured on RTX PRO 4500 for feasibility"; it is NEVER mixed into an
L4 table. Acceptance / match-rate / DTV / PPL are GPU-agnostic (modulo bf16
numerics) and valid here. The mamba-ssm / causal-conv1d / flash-linear-attention
fast-path kernels are NOT installed → both models run their naive/torch
fallback path (correctness-equivalent; only speed is affected, which does not
matter for GPU-agnostic E0 diagnostics). Falcon no-kernel seq cap stays 1024.

**Original diagnosis (kept for the record):**

**Discovered:** 2026-07-07, Pod A, first `nvidia-smi` + torch probe (CLAUDE.md
"before any CUDA work run nvidia-smi").

**Symptom:** every CUDA kernel dies with
`RuntimeError: CUDA error: no kernel image is available for execution on the device`.

**Root cause:**
- Pod A GPU = **NVIDIA RTX PRO 4500 Blackwell, 32 GB, compute capability sm_120**
  (confirmed by nvidia-smi; driver 580.167.08, CUDA 13.0).
- Installed `torch 2.4.1+cu124` ships kernels only for
  `sm_50 … sm_90`. `torch.cuda.is_available()` returns **True** (misleading), but
  any real kernel launch (even a 64×64 matmul) fails as above.

**Impact:** ALL GPU experiments are blocked: E0.1 smoke tests, E0.3 fp32 control,
E0.5 early-exit forensics (Phase 0), and everything in Phases 1–5. The no-GPU
Phase-0 work (v1 snapshot, E0.2 inventory doc, E0.6 normalization, the
`src/specdiag/` refactor, E0.4 static review + CPU toy test) is **not** blocked
and proceeds.

**Secondary env gaps found at the same time:**
- `transformers`, `datasets`, `accelerate`, `scipy` are **not installed** (only
  torch/torchaudio/torchvision present). PLAN §2.5.1's
  `revision/requirements_revision.txt` + `runpod_setup.sh` do not exist yet.
- `HF_TOKEN` is **not set** (needed for gated checkpoints, e.g. some Falcon-H1 /
  new-arch models).
- Mamba-2 / Griffin / conv-based new architectures (granite, recurrentgemma,
  lfm2, hymba, zamba2, samba) may need `mamba-ssm` + `causal-conv1d`, whose
  prebuilt wheels also **lack sm_120 kernels** → likely source builds for
  Blackwell (non-trivial; potential further blocker).

**Proposed fix (needs author decision — see day2_decision_gate / questions):**
Upgrade to a Blackwell-capable stack, e.g. `torch>=2.7` built against **cu128**
(`pip install torch --index-url https://download.pytorch.org/whl/cu128`), then
install pinned `transformers/datasets/accelerate/scipy`, and pin the result into
`revision/requirements_revision.txt`. Caveat (PLAN constraint 2): this GPU is
**not an L4**, so any *latency* number produced here is non-canonical
("measured on RTX PRO 4500 for feasibility") — but E0 de-risking (loadability,
patchability, acceptance/match-rate correctness) is GPU-agnostic and valid here.

**Status:** RESOLVED — torch upgraded in-place on this Blackwell pod; GPU-agnostic
E0 diagnostics proceed here. L4-canonical latency runs still deferred to an L4 pod.

## B_E52 — [RESOLVED 2026-07-19] RedPajama corpus for E5.2 (R2.4) fell back to C4

**Problem.** E5.2 is the contamination control R2 asked for: repeat the headline
result on a corpus *outside* WikiText, and R2 named `RedPajama-Data-1T-Sample`
verbatim. `src/specdiag/data.load_recent_corpus` could not load it, so it
silently degraded to **allenai/c4** — the frozen `acceptance_recent_corpus.csv`
is therefore C4 data, not RedPajama, weakening the "on the reviewer's own terms"
framing.

**Root cause (two layers).**
1. `togethercomputer/RedPajama-Data-1T-Sample` is now **404 on the Hub**
   (RepositoryNotFoundError), even authenticated — the Sample repo is gone.
2. Its live parent `togethercomputer/RedPajama-Data-1T` still exists but ships a
   **dataset loading script** (`RedPajama-Data-1T.py`) that `datasets>=5` refuses
   to execute — the generic failure mode behind the C4 fallback.

**Resolution — stream the real thing, bypass the script (PLAN approach a.1).**
New self-contained runner `experiments/e5_2_redpajama_real.py`:
- Reads the shard list `urls/common_crawl.txt` from the live parent 1T repo via
  `huggingface_hub.hf_hub_download`, then streams the raw `.jsonl.zst` shards
  with the plain `json` loader (`load_dataset("json", data_files=<url>,
  streaming=True)`) — **no remote code, no loading script**. Reads the `text`
  field, keeps the first 200 docs with len>100 chars (char-truncated to 2000, a
  prefix well above the 256-token cap the acceptance loop applies), streamed in
  ~3.5 s (MBs, not the full GBs).
- Needed `zstandard` (pip-installed; pure decompression lib, no data/weights
  touched) for the `.zst` shards.
- CommonCrawl is the dominant slice of RedPajama-Data-1T-Sample and the closest
  analogue to the C4 web-text run, so numbers are comparable.
- **No C4 fallback exists**: the loader only ever loads RedPajama, and before any
  result is written it asserts `"redpajama" in corpus label` and `hf_id` is not
  C4 — else it aborts (per the CRITICAL directive).

**Output (all NEW files; nothing frozen touched).**
`results/E5/acceptance_redpajama.csv` + `.meta.json`, and
`results/E5/perprompt/redpajama_real__<model>__k<k>.pkl`. The frozen C4 artefacts
(`acceptance_recent_corpus.*`, `perprompt/redpajama__*.pkl`) are left intact.

**Sanity (vs frozen C4: Falcon 0.60/0.415, Qwen 0.068/0.035).** Headline holds
on real RedPajama — Falcon-H1-0.5B sustains high acceptance, Qwen3.5-0.8B
collapses:
- falcon-h1-0.5b: A_2=0.5125, A_4=0.345
- qwen3.5-0.8b:  A_2=0.1125, A_4=0.055
Falcon stays high (A_2 in the expected 0.5–0.6 band); Qwen stays collapsed
(4.5–6.3x below Falcon). Absolute values shift modestly from C4 (Falcon a touch
lower, Qwen a touch higher) — expected for a genuinely different corpus
(RedPajama CC vs allenai/c4 differ in filtering/dedup/classifier), and the
opposite-direction shifts rule out a load/prompt bug (that would tank both
models). GPU: NVIDIA L4 (acceptance metric is GPU-agnostic; GPU recorded in meta
only, no L4 hard-fail per this being an acceptance experiment). No >2 h block.

## B_ATTNK — [RESOLVED 2026-07-19] attention_only c_eff under kernels (B-6) + fresh-pod stack rebuild

**Task (B-6).** Measure c_eff of the **attention_only** drafter (drafts with the
attention branch, SSM branch zeroed) on Falcon-H1-0.5B with the OFFICIAL
mamba-ssm/causal-conv1d kernels active + verified — same protocol as the
component_only "L4-kernels" run (`e_with_kernels.py`). Latency-sensitive →
hard-fail if GPU ≠ L4. GPU confirmed **NVIDIA L4** at startup.

**Infra reuse.** New sibling driver `experiments/e_with_kernels_attention.py`
(mirror of `e_with_kernels.py`), reusing `e3_partial.measure_c_eff` (draft-fwd
ms ÷ full-fwd ms, `use_cache=False`, CUDA events, post-warmup),
`e3_partial.acceptance`, `e3_partial.c_param_for`. Only the draft mode changes to
`attention_only`. S_theory(k=1) uses the **already-measured** τ̄₁ of
attention_only from the frozen L4 E3.1 row (`partial_drafter_ablation.csv`,
τ̄₁=0.5133). Output to a NEW file — no frozen artefact touched.

**Blocker encountered — this is an EPHEMERAL pod: the entire Python stack was
gone** (only torch survived on the persistent volume; `transformers`,
`huggingface_hub`, `einops`, `accelerate`, the mamba kernels — all missing). Had
to rebuild the canonical stack before measuring. Sequence (torch protected
throughout; verified `2.4.1+cu124` + CUDA launch after every step):
1. Source-built the kernels via the proven `rerun_kernels4.sh` recipe
   (`revision/build_kernels_only.sh`): `causal-conv1d==1.6.2.post1` +
   `mamba-ssm==2.3.2.post1`, `--no-build-isolation --no-cache-dir --no-deps`,
   `MAX_JOBS=4`, 45-min box. Built in ~11 min.
2. `--no-deps` dropped runtime deps; import gate then surfaced them one by one:
   `einops`, `huggingface_hub`/`transformers` (whole stack absent), and
   critically **triton 3.7.1** — mamba-ssm 2.3.2's `mamba3` module calls
   `triton.set_allocator` (triton≥3.5), but torch 2.4.1 ships triton 3.0.0. The
   frozen canonical env (`requirements_canonical_L4.txt`) pins triton==3.7.1,
   which is proven to coexist with torch 2.4.1+cu124 — installed it `--no-deps`.
   Restored the rest (`transformers==5.13.0`, `accelerate==1.14.0`, datasets,
   scipy, etc.) under a constraints file pinning torch/vision/audio/triton/mamba/
   causal so pip could never touch the compiled/canonical stack. All installs are
   off-the-shelf libraries → NOT kernel work (HARD CONSTRAINT 1 intact).
3. **Runtime fast-path gate PASSED:** log shows
   `The fast path for FalconH1 will be used when running the model on a GPU` and
   the `fast path is not available … Falling back to the naive implementation`
   warning is ABSENT → kernels genuinely active, numbers are true-kernels (not
   naive mislabeled). Final stack matches the canonical L4 freeze
   (torch 2.4.1+cu124, transformers 5.13.0, triton 3.7.1, mamba_ssm 2.3.2.post1,
   causal_conv1d 1.6.2.post1). No >2 h block.

**RESULT (canonical L4, kernels active, n=150 val-test).**
`results/E3.1/attention_only_kernels.csv` (+ `.meta.json`):
- **c_eff(attention_only, kernels) = 0.42314**  [t_draft=17.14 ms, t_full=40.51
  ms]; c_param=0.68627. NB vs the naive-path frozen L4 c_eff=0.04765: activating
  the fast SSM path speeds up the *full/verify* forward (t_full drops), so the
  draft/full ratio rises — the attention-branch draft gets no benefit from the
  SSM kernels, only the verifier does.
- **S_theory(k=1) = (1+τ̄₁)/(1+c_eff) = (1+0.5133)/(1+0.42314) = 1.06336 > 1.**
  Freshly re-measured τ̄ (0.5067) matches the frozen 0.5133 — kernels do not
  change which tokens accept, confirming consistency.
- k=2: A_2=0.3533, S_theory=0.93161 (<1).

**Reading.** Under the official kernels, attention_only is the *cheaper* drafter
(c_eff 0.423 vs component_only's 0.784) because zeroing the SSM removes a
genuinely heavy branch, whereas zeroing attention removes little. It clears
**S_theory>1 at k=1** where the kernel-active component_only run did not
(component_only S_theory(k=1)≈0.976). attention_only remains a parallel-arch
*diagnostic* with lower acceptance than the ssm_only headline, but it is a second
data point for R2 §2 / EiC "credible path to >1×": on Falcon-H1-0.5B a
parameter-free internal drafter crosses net-positive theoretical speedup at k=1
even with the fast SSM path making the verifier cheap.
